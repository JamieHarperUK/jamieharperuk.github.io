        Operational Overview

        How the tool works, where it fits, and what it protects.

        Oakshift WebEditor is a browser-based publishing surface for JSON-driven static sites. It is designed to keep client content changes local, explicit, and reviewable while still being easy to operate from a browser session.

        1

        Authenticate

        The user signs in with GitHub Device Flow. The editor keeps the token in session storage and uses the configured OAuth broker to complete the exchange safely.

        2

        Verify Repository Access

        The editor checks that the authenticated GitHub account can write to the configured repository. This prevents the tool from drifting into unrelated repos when transplanted for other client sites.

        3

        Load a Configured File

        Available JSON targets are taken from WEBEDITOR_CONFIG.repository.files. That means each deployment can expose one file or several, depending on the site structure.

        4

        Edit Using the Right Surface

        Use Drag & Drop for tree-level structure changes, CRM mode for record-based content maintenance, and Text mode for direct JSON control when exact syntax matters.

        5

        Commit One File at a Time

        Each save performs a latest-SHA check, writes a single targeted commit, and can optionally call a notification endpoint after a configured delay to allow published content to propagate first.

        Why this model works

        It gives clients and maintainers a constrained editing surface without requiring a bespoke CMS or a full backend. Git stays the source of truth, and the site can remain static.

        What CRM mode is for

        CRM mode assumes array or object records and favors content entry over syntax editing. Records can be reordered, duplicated, and edited through fields rather than raw JSON where possible.

        What still needs discipline

        The tool narrows risk, but it does not replace governance. File maps, schemas, notification tokens, and commit review practices still need to be set sensibly per client deployment.

        Per-site configuration

        To deploy this into another repository, update branding, set the target repository, define the file map, choose a default file key, and optionally connect a site-specific notification worker.

        • Change branding for the client identity.
        • Set repository.targetRepoFullName.
        • Populate repository.files.
        • Set repository.defaultFileKey.

        Notification support

        When enabled, the editor can call a Cloudflare Worker after commit. That worker can then handle subscriber state, VAPID-based push delivery, and optional delivery delay rules for the destination site.

        • Use a dedicated Worker per client or per product.
        • Keep notification auth separate from OAuth configuration.
        • Prefer rotating tokens over long-lived hardcoded secrets.
